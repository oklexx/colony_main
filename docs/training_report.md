## 2. Как выбирается лучшая модель (чемпион)

### 2.1 Механика (Task 3)

1. Каждые `eval_freq=100_000` шагов вызывается `_eval()`.
2. `_eval()` сохраняет текущую модель во временный файл, вызывает `run_eval()` с `normalization_path` и `map_size` (теперь = тренировочный).
3. `run_eval()` прогоняет `eval_episodes=10` эпизодов, возвращает `days/people/bases/avg_return`.
4. Если `result["days"] > self.best_eval_days` (или `best_eval_days is None`) — сохраняется `best_model.pt` + `best_model.meta.json`.
5. `best_eval_days` — **максимум по `days`** среди всех eval за прогон.

### 2.2 Критерий отбора

**`days` (средняя продолжительность жизни колонии в днях)** — единственный критерий.
`people`, `bases`, `avg_return` логируются, но НЕ влияют на отбор.

### 2.3 Отклонения / проблемы

| # | Проблема | Серьёзность |
|---|---|---|
| 1 | **run_004 best_model: `eval_return=−2689`, `eval_bases=1.0`** — модель с 1 базой и отрицательным return выбрана как лучшая по `days=1487`. Вероятно, эпизод "выжил" за счёт не-смерти (не game_over), но колония не развивалась. Критерий `days` без ограничения по `bases`/`return` даёт ложный чемпион. | **Высокая** |
| 2 | **`best_eval_days` не сбрасывается при fine-tuning (resume)** — run_002_ft наследует `best_eval_days` от родительской модели и может не переписать `best_model.pt`, если новый eval не превзойдёт старый. | Средняя |
| 3 | **eval на `map_size=200`, а тренировка тоже на 200** — совпадает (OK после фикса). Но C++-дефолт 280, UI-дефолт 200 — если пользователь не меняет, eval=200=training (OK). Если пользователь поставит 280 в training, eval тоже 280 (OK, т.к. `_eval` передаёт `cfg.map_size`). | Низкая |
| 4 | **`avg_return` в eval — raw reward**, а в training — normalized (C++ `rew_rms`). Метрики не сопоставимы. | Низкая |
| 5 | **10 эпизодов eval — мало для стабильной оценки.** Дисперсия `days` между эпизодами может быть высокой (видим 365↔979 в run_003). | Средняя |

## 4. Идеи по улучшению обучения

### 4.1 Критерий отбора чемпиона (приоритет: ВЫСОКИЙ)

1. **Композитный скоринг вместо одного `days`:**
   ```
   score = days × 0.4 + bases × 10 × 0.3 + people × 0.2 + max(0, avg_return) / 10000 × 0.1
   ```
   Или: `score = days` только если `bases >= 5` и `avg_return > 0`.

2. **Штраф за бездействие:** если `bases < 3` или `return < 0` — не считать eval успешным.

3. **Минимальный порог `bases`:** чемпион должен иметь >= N баз (напр., 5), иначе — отклонить.

4. **Медиана вместо среднего по eval:** использовать median `days` из 10 эпизодов (устойчиво к аутлайерам).

5. **Увеличить `eval_episodes` до 20–30** для стабильной оценки.

### 4.2 Награды (приоритет: ВЫСОКИЙ)

6. **Штраф за бездействие (idleness penalty):** если N дней подряд нет строительства/продаж — `−X` за день.

7. **Пороговая награда за развитие:** `+50` при достижении 5 баз, `+100` при 10, `+200` при 20 (milestone rewards).

8. **Штраф за отрицательный net-worth:** `−Y × max(0, −net_worth) / 1000`.

9. **Увеличить `game_over_penalty`** до 50–100, чтобы "зомби-выживание" было менее выгодно.

10. **`survival_bonus` включить (0.01/день):** поощрять выживание, но малым весом, чтобы не доминировало.

### 4.3 Гиперпараметры (приоритет: СРЕДНИЙ)

11. **LR schedule:** linear decay или cosine annealing к концу обучения.

12. **`n_steps` увеличить до 4096** (больший rollout → стабильнее GAE).

13. **`ent_coef` выше (0.05)** на ранних этапах для exploration.

14. **`gamma` 0.995** вместо 0.99 (дальше видит reward).

15. **`vf_coef` 0.5** вместо 1.0 (меньше шума в value).

### 4.4 Архитектура (приоритет: НИЗКИЙ)

16. **3 скрытых слоя (256-256-256)** вместо 2 — больше ёмкости.

17. **LayerNorm** в trunk.

18. **Separate value head** (отдельная сеть для value) — уменьшает конфликт градиентов.

### 4.5 Данные / среда (приоритет: СРЕДНИЙ)

19. **Random seed на каждый прогон** — уже реализовано (чекбокс).

20. **Курикулум** — см. ниже.

21. **Data augmentation:** случайные перестановки ресурсов в obs (если допустимо).

## 5. Ответы на вопросы

### 5.1 Случайный сид для карты

**Мнение: ДА, нужно.**

- Уже реализовано: чекбокс 🎲 random в UI генерирует сид при активации и при каждом запуске.
- **Но:** сид влияет на **распределение ресурсов на карте** (расположение земли, воды, руд). Разные карты → разные стратегии.
- **Рекомендация:** при обучении использовать **несколько разных сидов** (напр., 5–10) и усреднять eval по ним. Это даст обобщающую модель, а не переобученную на одну карту.
- **Реализация:** `n_seeds=5` в конфиге, каждый eval прогоняет 10 эпизодов × 5 сидов = 50 эпизодов.

### 5.2 Курикулум

**Мнение: ДА, очень нужно.**

Текущий `curriculum_stage=0` — все здания доступны с начала. Это плохо:
- Агент тратит время на случайные действия
- Не учится приоритетам (еда → энергия → промышленность)

**Рекомендуемый курикулум:**

| Stage | Что открыто | Цель |
|---|---|---|
| 0 | House, Farm, WaterChannel | Выживание (еда + вода) |
| 1 | + PowerStation, Coalmine | Энергия + топливо |
| 2 | + Sawmill, Ironmine, Refinery | Промышленность |
| 3 | + City, BigHouse, Goldmine | Масштабирование |

**Реализация:**
- `curriculum_stage` в конфиге (уже есть)
- `unlock_ids` — список открытых зданий (уже есть)
- Переключение stage каждые N шагов (напр., 5M)
- Eval на текущем stage (не на полном)

**Плюс:** агент учится последовательно, не путается в 25+ типах зданий сразу.

### 5.3 Как улучшить отбор чемпиона

См. раздел 4.1. Кратко:
1. Композитный скоринг (days + bases + people + return)
2. Минимальный порог bases (>= 5)
3. Медиана вместо среднего
4. Больше eval эпизодов (20–30)
5. Штраф за "зомби" (bases < 3 или return < 0)

### 5.4 Просмотр игры чемпиона через UI

**Мнение: ДА, критически важно для отладки.**

**Реализация:**

1. **Новая вкладка/кнопка "Наблюдение"** в UI.
2. Загружает `best_model.pt` + `normalization.json`.
3. Создаёт `CppColonyEnv` с тем же `map_size`.
4. Прогоняет эпизод **пошагово**, рисуя состояние:
   - Карта (здания, ресурсы, люди)
   - Действие агента (какое здание построил / что сделал)
   - Reward за шаг
   - День/месяц/год
5. **Регулировка скорости:**
   - Sliders: 1x, 2x, 5x, 10x, 50x, 100x (шагов/сек)
   - Pause / Step / Resume
6. **Технически:**
   - `CppColonyEnv` уже поддерживает `step(action)`
   - Рендер — через Raylib (уже есть `src/gui.cpp`) или matplotlib (проще)
   - Альтернатива: headless прогон + запись в JSON → визуализация в браузере

**Простой вариант (MVP):**
- Консольный прогон: `python watch_champion.py --model best_model.pt --speed 10`
- Печатает каждый шаг: день, действие, reward, bases, people
- Скорость — sleep между шагами

### 5.5 Автоматический агент-наблюдатель (auto-tuning)

**Мнение: ДА, это следующий логический шаг.**

**Концепция:**
1. **Обучающий цикл (orchestrator):**
   - Запускает прогон с параметрами A
   - По завершении читает `meta.json` + `best_model.meta.json`
   - Оценивает результат (композитный скоринг)
   - Если результат хуже предыдущего — пробует параметры B (свой следующий прогон)
   - Если лучше — фиксирует как лучшего
   - Повторяет N раз

2. **Поиск параметров:**
   - **Grid search** (простой): заранее заданные комбинации
   - **Random search** (лучше): случайные комбинации из допустимого диапазона
   - **Bayesian optimization** (оптимально): `scikit-optimize` или `Optuna`
   - **Evolutionary** (для сложных случаев): NSGA-II

3. **Критерий остановки:**
   - N прогонов (напр., 20)
   - Время (напр., 12 часов)
   - Улучшение < ε M прогонов подряд

4. **Реализация:**
   ```python
   # auto_trainer.py
   for i in range(n_runs):
       params = suggest_params(i)  # random/bayesian
       run_training(params)       # subprocess worker.py
       result = read_meta()       # parse meta.json
       score = composite_score(result)
       if score > best_score:
           best_score = score
           best_params = params
           save_champion()
   report(best_params, best_score)
   ```

5. **Параметры для оптимизации:**
   - `learning_rate` (1e-4 … 1e-3)
   - `n_steps` (1024 … 8192)
   - `batch_size` (4096 … 65536)
   - `ent_coef` (0.005 … 0.05)
   - `vf_coef` (0.3 … 1.0)
   - `gamma` (0.99 … 0.999)
   - `net_arch` (256/512/1024)
   - `reward` (weights)
   - `curriculum_stage` / `unlock_ids`

6. **Плюсы:**
   - Не нужно сидеть и запускать вручную
   - Систематический поиск
   - Отчёт по всем прогонам
   - Автоматический выбор лучшего

7. **Минусы:**
   - 1 прогон = 4–45 минут → 20 прогонов = 1.5–15 часов
   - GPU занят на всё время
   - Нужно следить за дисками (чекпоинты)
