## Часть 2. НОВЫЕ находки — C++ env (`src/env.cpp`, `env.h`, `constants.h`)

### N1. 🎯 Знак `manual_tax_penalty` инвертирован — «штраф» даёт бонус
`env.cpp:908-910`:
```cpp
action_name = "MGR:manual_tax";
rew -= cfg_.manual_tax_penalty;   // manual_tax_penalty = -0.5  →  rew += 0.5 !
```
Все остальные штрафы применяются как `rew += cfg_.error_penalty` (сложение с отрицательным). Здесь `-=` с отрицательным значением = **бонус +0.5 за ручную оплату налога**. Комментарий на `:921` («PAY_TAX = advance 1 day + tax penalty») прямо противоречит коду. Комментарий в `env.h:38`: «cost of manual tax payment».
**Фикс:** `rew += cfg_.manual_tax_penalty;` (и счётчик `c_manual_tax += ...`).

### N2. 🎯 Три источника дефолтов наград; `from_dict` — outlier (усиление B1)
Проверено построчно: **датакласс Python = C++ `RewardConfig` (env.h:21-61) = `configs/reward.json`** — все 29 значений совпадают (1.0/1.0/0.5/15/1.0/0.2/0.3/0.0/10/8/−1/0/−3/−0.5/0.0001/−10/3/0.01/30/2/2/5/0.5/±50). Расходится только `RewardConfig.from_dict` (`config.py:85-104`): daily_income 0.3, survival_bonus 0.1, survival_coeff 0.001, milestone 10, клип ±10. Любой `--reward-config partial.json` молча подмешивает эти 5 значений, отличные от всего остального проекта. Фикс B1 (через `cls()`) устраняет расхождение полностью.

### N3. 🎯 Хардкоженные веса наград в обход RewardConfig (`env.cpp`)
Не настраиваются через reward.json и не видны в конфигах:

| Строка | Что | Значение | Комментарий |
|---|---|---|---|
| 716, 722 | Неуплата годового/главного налога (нет денег) | **−5.0** | ×5 от error_penalty |
| 940 | Долг | −0.02 × credit/1000 | «Increased from 0.005» |
| 941 | Рождение/прибытие человека | **+1.0** каждый | сравнимо с build_bonus |
| 942 | Смерть | **−20.0** каждый | 3 смерти = −60 → упирается в клип −50: градиент «избегать смертей» насыщается |
| 943 | Потеря базы | **−30.0** | |
| 944 | Переполнение жилья | −2.0 | |
| 973 | Бонус за дом при нехватке жилья | 3.0 × log1p((people−housing)/10) | |
| 985, 998 | Бонус за ферму/канал при нехватке еды/воды | 2.0 × log1p(idle/5) | растёт с простоем |

Рекомендация: вынести в `RewardConfig` (хотя бы death_penalty, tax_fail_penalty, born_bonus, base_lost_penalty) — иначе «тюнинг наград» через JSON настраивает только половину функции.

### N4. `tax_due_days_` и `days_since_last_build_` считают действия, а не дни
`env.cpp:1089-1092`: `tax_due_days_ += 1` на **каждом шаге** с просроченным налогом; game over при `>= TAX_GRACE_DAYS (60)`. Но `WEEK` продвигает 7 дней за 1 шаг → «60 дней отсрочки» на деле от 60 дней (все DAY) до **420 дней** (все WEEK). Аналогично `days_since_last_build_ += 1` (`:1081`) — idle-порог «3 дня» = 3 действия (WEEK растягивает до 21 дня). Не катастрофа (все действия и так двигают время), но семантика констант плывёт; в UI/obs поле `tax_due_days` (`:1167`) показывает счётчик шагов под именем «дни».
**Фикс (если нужна точность):** инкрементировать на число реально прошедших дней (`results.size()` для WEEK = 7).

### N5. Ловушка idle-штрафа при банкротстве
`:1107-1111`: каждые 3 действия без постройки → −10 (после чего счётчик сбрасывается, т.е. −10 каждые 3 шага постоянно). Если у агента кончились деньги — все BUILD-действия **замаскированы** (`env.cpp:580` money check), строить невозможно, а штраф капает бесконечно. Единственный выход — копить через DAY/WEEK, но агент в этой яме получает −10/3 шага без возможности исправить. В связке с N3-бонусами «построй ферму при нехватке еды» (которые тоже недоступны без денег) — локальный минимум, из которого политика может не выбраться. Рекомендация: не применять idle-штраф, когда ни одно BUILD-действие недоступно (проверить по маске), либо снизить до −2…−3.

### N6. Клип награды ±50 применяется **до** нормализации — порядок корректен
`:1146` clamp по `clip_reward_min/max` → `:1303` `rew_rms_` нормализация с клипом ±10. Здесь всё правильно (отмечаю, чтобы не «чинили»).

## Часть 3. НОВЫЕ находки — evaluator и train_ui

### N7. 🎯 Optuna-поиск гиперпараметров оптимизирует сломанную цель
`auto_trainer.py:87-98` берёт objective из `best_model.meta.json → best_score`. Этот score считается eval'ом **без нормализации obs** (B2) и на **76% состоит из дней выживания** (F3). Итог: весь автоматический поиск параметров ранжирует эксперименты по зашумлённой метрике «кто дольше прожил без нормализации». Чинить B2+F3 нужно **до** любых прогонов auto_trainer.

### N8. `run_eval` читает reward-конфиг из meta, которого не существует
`evaluator.py:158-170`: ищет `meta["config"]["reward"]` в `best_model.meta.json`/`meta.json`. `_eval` пишет в meta только score/days/bases/… — ключа `config` нет → `reward_cfg` всегда `None` → eval-среда создаётся с дефолтными наградами. На динамику (days/people/bases) не влияет, но `avg_return` в eval считается по другим весам, чем в тренировке → порог `eval_min_return` сравнивается с несопоставимой величиной.
**Фикс:** в `_eval` при сохранении meta добавлять `"config": {"reward": self.cfg.reward.to_dict()}`.

### N9. Политика нормализации в evaluator несогласована между режимами
`evaluator.py:172-188`: flat — при отсутствии файла **raise** («Refusing to run eval on un-normalized observations», правильно); hybrid — при отсутствии файла **молча пропускает**; minimap — нормализация не применяется вовсе. Для minimap это ок (модель не видит flat-obs), для hybrid — flat-компонента останется ненормализованной без предупреждения.
**Фикс:** в hybrid-ветке при отсутствии файла — raise или хотя бы warning (как в flat).

### N10. Пересечение сида eval с тренировочной средой
`cpp_vecenv.py:140`: тренировочные env получают сиды `42, 10042, 20042, ...`; `run_eval` (`evaluator.py:210`): эпизоды `seed+ep` = `42, 43, ..., 61`. **Eval-эпизод 0 играет на той же карте/событиях, что стартовый тренировочный env 0** → небольшая утечка запоминания в метриках (особенно на 1-м env при коротких прогонах). Фикс: сдвинуть eval-сиды (например, `seed + 500000 + ep`).

### N11. Приоритет CLI-флагов над reward-JSON (минор)
`cpp_vecenv.py:75-77`: `rc.disable_net_worth = disable_net_worth` выполняется **после** применения словаря → `--disable-net-worth=False` (дефолт) перезапишет `"disable_net_worth": true` из JSON. Фикс: применять флаги только если они явно переданы.

## Часть 4. НОВЫЕ находки — конфиги и нагрузка на систему

### N12. 🎯 `exp_25/26/27`: n_envs=1024 → 56+ ГБ VRAM. Это источник «сильной нагрузки»
Расчёт по живому коду буфера (`rollout_buffer.py`, `_TensorRolloutBuffer`):
```
n_envs=1024 × n_steps=2048 = 2 097 152 шагов
minimap obs: 2 097 152 × 8×29×29 × 4B ≈ 56.4 ГБ   (exp_25/27 — невозможно ни на одной одиночной GPU)
hybrid:      +1.8 ГБ flat → ~58 ГБ                 (exp_26)
+ action_masks 0.4 ГБ + остальное
```
Плюс 1024 C++ Game-инстанса с картой 200×200 и JSON-конфигами на каждый. Если эксперименты запускались из этих конфигов — OOM/своп/«тормозит вся система» гарантированы. **Рекомендация:** для minimap/hybrid на одной GPU: `n_envs 16–64`, `n_steps 256–512` (буфер 0.9–3.5 ГБ); большие батчи набирать эпохами, не объёмом буфера. Для flat-режима текущие дефолты (8×4096) адекватны.

### N13. Прочее по конфигам
* `reward.json` не содержит `disable_provider_bonus` — дефолт false, консистентно ✓.
* exp-конфиги используют `ent_coef 0.01, gae_lambda 0.95, gamma 0.99, vf_coef 1.0, max_grad_norm 1.0, net [512]` — сами значения здоровые; проблема только в n_envs/памяти. Дефолты `Config` (0.05/0.98/0.995/0.5/0.5/[256,256]) хуже — рекомендую привести дефолты к exp-значениям (кроме vf_coef: 0.5 достаточно).
