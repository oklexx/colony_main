## 1. Экспертный вердикт

### (a) Бонус за добычу определённого ресурса — **валидно**, при 3 условиях

Это классический *subgoal shaping* (декомпозиция цели «колония, работающая
годами» на наблюдаемые промежуточные события). Работает, потому что:

1. **Триггер — событие производства работающим зданием**, а не уровень склада.
   Покупка ресурса на рынке (BUY_FOOD, MGR:sell/buy) бонуса не даёт —
   склад «накачать» нельзя.
2. **Вес ресурса = спрос**: `w(r) = min(1.0, 0.25 × число типов зданий,
   потребляющих r)`. Вода/дерево/нефть (4+ потребителя) → 1.0; еда/золото
   (никто не потребляет) → 0.0. Иначе модель честно нашла бы, что спам-фермы
   еды дают бесконечную «добычу».
3. **Разовость + насыщение**: `first_extraction` — один раз за эпизод и
   ресурс; `extraction_daily` — каждый день, пока работает производитель,
   но с насыщением по числу производителей (1 = 33%, 2 = 67%, 3+ = 100%).
   «Копать в стол» сверх 3 одинаковых зданий наград не добавляет.

Почему это лечит диагностированную болезнь (из `ANALYSIS_TRAINING_REPORT.md`):
модель не строит *цепочки*, потому что первый день работы производителя
даёт ~0 на фоне log2-шума, а `chain_bonus` срабатывает только когда
потребитель уже работает. `first_extraction` подставляет **первую ненулевую
точку** на траектории цепочки: дорога → вода → ферма начинает работать →
+3.0 → дальше `chain_bonus`. Это классический «мост» в reward shaping,
не меняющий глобальный оптимум (он остаётся «выжить и наращивать сеть
производств»), но делающий его достижимым для PPO.

### (b) Штраф за «неверную активность» — **валидно только как точечные
стоимости действий**, а не как генеральный штраф

Штраф за «неверность» требует, чтобы среда знала, что *верно*. Универсального
критерия нет, и попытка придумать (например, «строительство без роста сети —
штраф») убивает exploration: модель перестанет пробовать.

Что валидно и что реализовано — **стоимость конкретного действия,
создающего артефакт**:

| Действие | Артефакт, который ломаем | Реализация |
|---|---|---|
| TAKE_LOAN (успешный) | кредитный луп «+50k кассы → сидеть», найденный в phase-1: при `survival_coeff=0` касса бесплатна, а процент 0.2%/день слишком мал | `loan_penalty` на успешный кредит + `debt_coeff 0.1` (в v2 было 0.02): 50k долга = −10/день, луп становится убыточным |
| PRESERVE / UNPRESERVE | «жонглирование» сохранением: в v2 `preserve_penalty` был **мёртвым ключом** (объявлен, но нигде не применялся), действие бесплатное | `preserve_penalty` теперь реально вычитается в обоих направлениях |

Что **не** реализовано сознательно: штраф за «неверную постройку» (что такое
«неверная» — не определено без внешней цели), штраф за бездействие (убьёт
осмысленный анализ ситуации), штраф за ошибки *вообще* (`error_penalty`
уже существует с v1).

### Что НЕ делает v3

- Не меняет глобальную цель (выживание, налоги, сеть производств) — только
  добавляет промежуточные точки и убирает два бесплатных артефакта.
- Не отменяет выводы phase-1: `entropy_coef 0.05 → 0.01`, `gamma 0.997 →
  0.999`, налог-шрейпинг, фикс resume — всё это обязателен **до** A/B,
  иначе v3 не отделяется от шума.

## 2. Формулы

```
w(r) = min(1.0, 0.25 × n_consumer_types(r))          # спрос на ресурс
      # вода/дерево/нефть → 1.0; еда/золото → 0.0

first_extraction(r) = first_extraction_bonus × w(r)
    # ровно один раз за эпизод на ресурс; срабатывает в первый день,
    # когда хотя бы одно работающее здание производит r
    # (WEEK-шаг: если был в любом дне недели)

extraction_daily(r) = extraction_daily × w(r) × sat(n_producers(r)) × n_days
    sat(k) = min(1.0, k / 3)                          # 1→33%, 2→67%, 3+→100%
    # n_days = число дней в шаге (DAY=1, WEEK=до 4)

need_fill(build) = need_fill_bonus × w(r)
    # при УСПЕШНОЙ постройке здания, производящего r, если
    # сейчас есть работающее здание с need_sunduk по r
    # (тот же критерий голода, что в Base::begin_day)

loan_cost  = −loan_penalty                              # на успешный кредит
preserve_cost = −preserve_penalty                       # PRESERVE и UNPRESERVE
debt_interest = −debt_coeff × credit                    # ежедневно (v2→v3: 0.02→0.1)
```

**Анти-эксплойты:**
- добыча через рынок/склад не наградима (триггер = работающее здание);
- еда/золото с весом 0 не наградимы (спам-фермы невыгодны);
- `need_fill` требует и стройки, и голодающего потребителя — «настроить
  голод и бесконечно строить» невозможно: после постройки ресурс
  появляется, `need_sunduk` гаснет;
- разовость `first_extraction` + насыщение `extraction_daily` — нет роста
  наград от количества одинаковых зданий сверх 3.

| `train.py`, `train_ui/worker.py`, `train_ui/main_window.py` | phase-1 resume-фиксы (несмешивать: это отдельный слой) |

**C++ дефолты — 0.0 (v3 выключено):** старый `configs/reward.json` ведёт себя
как v2, кроме `preserve_penalty` (теперь реально действует — это багфикс, а не
new feature; в v2-профилях его дефолт 0.0 в JSON сохраняется).

### Ключевые решения

1. **`extract_weight_` считается в `compute_catalog()`** — один раз на
   смену каталога (curriculum/unlock), а не каждый шаг.
2. **Снапшот производителей по сезонам**: WEEK-шаг покрывает до 4 сезонов;
   `ever_produced` = OR по дням, `day_producers` = последний день.
3. **`need_fill` в ветке постройки, до `advance_day`** — голод проверяется по
   флагу `need_sunduk` последнего прожитого дня (тот же, что видит игрок).

## 5. Протокол валидации (A/B на GPU)

Скриптованная A/B **не доказывает** эффект обучения (политика фиксированная) —
она показывает только разложение награды. Доказательство даёт PPO:

**Конфиг A (база):** P1-фиксы (resume, ent 0.01 аннелинг, γ 0.999, tax shaping)
+ `configs/reward.json` (v2).
**Конфиг B (v3):** то же + `configs/reward_v3.json`.

Протокол:
1. 3 сида × ≥5M шагов каждый, одинаковые eval-параметры.
2. **Сравнивать метрики, а не сырой return** (reward-функции разные!):
   - `eval_metrics: chains_activated` (прямая цель),
   - медиан/25-перцентиль дней до game over по 16 eval-эпизодам,
   - `base_count` к 365 дню, `money@365`,
   - количество циклов «дорога→производитель» в step_log (парсинг `BUILD:`),
   - `reached_resources` (новый метрик v3).
3. Критерий успеха B: `chains_activated` и p25-дней статистически выше
   (bootstrap CI по 16 eval-эпизодам), без деградации `money@365`.
4. Если B лучше: фиксировать v3; если нет — раздельно включать блоки
   (только extraction / только loan+preserve), чтобы найти виноватый.

**Мониторинг во время обучения** (step_log + `exp_analysis.py`):
- доля `extr=` в сумме награды по этапам (ожидание: растёт к концу,
  но не >40% — иначе shaping захлёбывает intrinsic reward);
- число TAKE_LOAN на 1000 шагов (ожидание: падает в B против A);
- энтропия (ожидание: не выше, чем в A).

## 6. Риски и как их гасить

| Риск | Митигация |
|---|---|
| `first_extraction` 3.0 — большая разовая награда, может «притянуть» политику к воде раньше, чем к жилью | вес w и разовость; при A/B падении — снизить до 1.5 |
| `need_fill` учит «лечить голод» любой постройкой (не обязательно правильной цепочкой) | требует реального голода + w(r); это и есть целевое поведение |
| `debt_coeff 0.1` может пережать осмысленное кредитование на старте | credit 0.2%/день × 0.1 = 0.02%/день эффективная цена — мягко; смотреть `money@365` |
| Новые ключи потеряются при старой сборке pyd | `CppVecEnv` уже предупреждает «stale pyd»; тест `test_v3_keys_roundtrip_python` |
| v3 накладывается на v2-настройки в `async_trainer` (variance penalty, tournament) — независимы | да, турнир и variance-штраф — селекция моделей, не reward; совместимы |

## 7. UI и единый конфиг (phase-3)

### 7.1. Что было (двоякость дефолтов)

До phase-3 значения наград по умолчанию тянулись из **пяти** мест:

| Источнику | Содержал | Проблема |
|---|---|---|
| `rl/config.py` (dataclass) | v3-значения (4 ключа) + v2-значения (error −1.0, debt 0.02) | половина v3, половина v2 |
| `REWARD_SPECS` (`parameter_widget.py`) | 34 спиннера, **v3-ключей не было** | v3-поля невидимы в UI; `_collect_config()` их не собирает → **параметры не долетают** |
| `configs/reward.json` ≡ `reward_v2.json` | v2 | никуда не автозагружаются, но выглядят «как дефолт» |
| `configs/reward_v3.json` | v3 | никуда не автозагружается |
| C++ `RewardConfig` (`env.h`) | v2 + v3-ключи = 0.0 (выкл) | расходится с Python-дефолтами |

Итог: пользователь видел в UI v2-набор без v3-полей, «По умолчанию» сбрасывало
к смесии v2/v3 из dataclass, а C++-бинары без JSON запускались с v2.

### 7.2. Что стало (один источник: `configs/reward_v3.json`)

**Канонический профиль — `configs/reward_v3.json`.** Все дефолты наград
зеркалируют его, а при наличии валидного файла он ПОВЕРАЕТ:

- `rl/config.py`: `load_default_reward_config()` / `default_reward_profile_path()`;
  `RewardConfig.from_dict()` при отсутствующих ключах заполняет **из профиля**
  (единственная точка fallback); dataclass-дефолты доведены до профиля
  (error −2.0, debt 0.1).
- `env.h` (C++): дефолты доведены до профиля (включая v3-ключи 3.0/0.3/1.5/0.5)
  — console/GUI-бинары без JSON тоже стартуют с v3. **Нужна пересборка pyd.**
- `train.py`: без `--reward-config` — `load_default_reward_config()`,
  в логе видно, какой профиль взят.
- `reward.json` / `reward_v2.json` — исторические профили старых экспериментов;
  автозагрузка ни где, только явный `--reward-config`.

### 7.3. Изменения UI

- **4 новых поля с русскими подписями** (`parameter_widget.py`, секция «Награды»):
  «Бонус первой добычи», «Добыча ежедневно», «Бонус закрытия потребности»,
  «Плата за кредит» — с tooltip'ами про веса/насыщение/анти-эксплойты.
  Точка: в `REWARD_SPECS` теперь ВСЕ ключи профиля (кроме `disable_*`-флагов,
  которые проходят через reward-dict без спиннеров).
- **Старт UI**: награды = (1) сохранённое состояние текущей версии UI →
  (2) профиль v3 → (3) дефолты кода. `CONFIG_VERSION` 6→7: сохранение
  старше v7 (v2-эра) для блока наград перезаписывается профилем — новые
  v3-поля сразу подгружаются в UI. В логе видно, что подгружено.
- **«По умолчанию» / «Сбросить»**: блок наград сбрасывается к профилю v3.

  (полный формат, идентичный тому, что получает worker: все гиперпараметры +
  38 reward-ключей + `config_version`); файл можно загрузить обратно или
  передать в `train.py`/worker как `--config`.
- **Загрузка старого файла** («Загрузить конфиг»): ключа нет в файле →
  значение подтягивается из профиля v3 (stale-фикс: v3-поля больше не остаются
  с предыдущим значением).
