## CRITICAL / MAJOR

### [C-E1] `reset()` не сбрасывает кэш чистой стоимости → искажение награды (env.cpp)

**Место:** `src/env.cpp:140-152` (`ColonyEnvCpp::reset`) и `src/env.cpp:348-362` (`net_worth`).

**Суть.** `net_worth()` кэширует результат:
```cpp
348:    if (net_worth_valid_) return cached_net_worth_;
...
361:    cached_net_worth_ = v;
362:    net_worth_valid_ = true;
```
В конце каждого шага `net_worth()` пересчитывается и ставит `net_worth_valid_ = true`
(env.cpp:361-362). `reset()` (env.cpp:140-152) создаёт **новый** `game_`, но
`net_worth_valid_` остаётся `true` со значением из **предыдущего эпизода**. На первом
шаге нового эпизода `net0 = net_worth()` (env.cpp:479) вернёт кэш прошлой игры (напр.
50 000), хотя реальная стоимость колонии — стартовая (~несколько тысяч).

Компонент награды:
```cpp
597:        rew += 0.005 * (net_worth() - net0 - (double)built_price);
```
оказывается неверным на ~`0.005 * 45000 ≈ 225` очков в самом начале каждого эпизода
после первого. Для RL это **сильно смещает обучение** (награда за «первый шаг» зависит
от прошлой игры, а не от текущей).

**Дополнительно (тот же корень):** внутри шага уплата налога (env.cpp:463-478) и
авто-обслуживание (env.cpp:661-671) меняют `money`/`live_time`, но **не вызывают
`invalidate_net_worth()`**. Между пересчётом кэша в конце предыдущего шага и чтением
`net0` в начале следующего `net_worth_valid_` остаётся `true`, поэтому `net0` «не видит»
налог, уплаченный в начале шага → систематическое занижение/завышение shaping-награды.

**Правильный вариант:**
```cpp
void ColonyEnvCpp::reset(int64_t seed) {
    game_ = Game(*base_data_, *events_data_, seed, map_size_);
    net_worth_valid_ = false;     // <-- добавить
    cached_net_worth_ = 0.0;      // <-- добавить
    steps_ = 0;
    ...
}
```
И вызывать `invalidate_net_worth()` после каждой мутации `money`/`bases`/`sunduk`
(налоги, авто-обслуживание). Либо сделать `net_worth()` всегда пересчитываемой
(без кэша), раз она и так вызывается каждый шаг.

**Серьёзность: critical** (не краш, но ломает детерминизм награды и RL-обучение).

### [M-E1] Недетерминизм: `rng` и `rng_np` сеются одним seed (game.cpp)

**Место:** `src/game.cpp:74-76`
```cpp
74:       earth(seed, map_size),
75:       rng(seed),
76:       rng_np(seed),
```
Оба генератора (MtRandom `rng` и PCG64 `rng_np`) стартуют с **одного** `seed`. Это даёт
коррелированные потоки (рождения/смерти и события/прибыль связаны одним зерном). Для
чистой воспроизводимости обычно берут `rng_np(seed ^ 0x9e3779b9...)` или отдельное зерно.
**Серьёзность: minor.**

### [M-E3] Поведение `advance_week` на границе уплаты налога (game.cpp / env.cpp)

**Место:** `game.cpp:429-438` + `env.cpp:581-586`. Если неделя пересекает 1 марта/1 ноября,
`advance_day` внутри недели натыкается на `check_advance()==annual_tax` и прерывает неделю
**до** симуляции этого дня. День уплаты налога тогда не проигрывается внутри недели, а
уплачивается отдельным шагом позже — на 1 день «задержка». Семантика недели отличается от
последовательности дней. Стоит явно обрабатывать налог внутри `advance_week`.
**Серьёзность: minor.**

## MINOR / потенциальные (проверить)

### [m-E1] UB сдвига: `BIRTH_DAYS >> n_puerp` (game.cpp)

**Место:** `src/game.cpp:318`
```cpp
318:     int64_t birth_days = BIRTH_DAYS >> n_puerp;
```
Если построено ≥64 «Роддома» (`Puerperal`), сдвиг на величину ≥ ширины `int64_t` —
неопределённое поведение. Есть защита `if (birth_days < 1) birth_days = 1;` (game.cpp:319),
но сам сдвиг уже UB. Правильно:
```cpp
if (n_puerp >= 63) birth_days = 1;
else birth_days = BIRTH_DAYS >> n_puerp;
```
**Серьёзность: minor** (нужно экстремальное число роддомов).

### [m-E4] Зависимость от строковых ID из данных (проверить по bases.json)

Код жёстко использует константы, которые **должны совпадать** с `id` в данных:
- `DEPOT_ID` (game.cpp:91, env.cpp:47), `ROAD_ID`, `MAX_ROADS` (env.cpp:47,496);
- `"Puerperal"` (game.cpp:314) — должен точно совпадать с `id` роддома, иначе рождаемость
  не работает;
- `BUILD_SUBSET` и списки `CURRICULUM_STAGE_1..3` (env.cpp:17-27,45) — если ID в данных
  отличаются (регистр/опечатка), постройки тихо исключаются из пула;
- порядок `SUNDUK_CAPTIONS` (game.cpp:17) должен совпадать с
  `{"gold","food","coal","iron","oil","stone","water","wood","energy"}`.

**Проверено по `configs/bases.json`** (см. `04_data_config_inconsistencies.md`): все 32
не-городских `id` из `bases.json` входят в `BUILD_SUBSET`; `City` исключается; `image_index`
0..32 совпадает со спрайтами. Расхождений в ID на данный момент **не найдено** — но это
хрупкая зависимость (stringly-typed), рекомендуется centralize.

**Серьёзность: minor** (при текущих данных OK).

### [m-E5] Порядок перечисления `Season` (env.cpp / constants.h) — ПРОВЕРИТЬ

**Место:** `src/env.cpp:97-105` (`python_season_to_cpp`) предполагает
`SEASON_SPRING=0..SEASON_WINTER=3`. Однако `include/colony/constants.h:56` содержит
`enum Season { SEASON_SUMMER=0, SEASON_AUTUMN=1, SEASON_WINTER=2, SEASON_SPRING=3 }`
(порядок «лето=0»). В `env.cpp:413-418` наблюдение кодирует `season/3` (spring=0 по
порядку записи в obs), а `python_season_to_cpp` делает identity-маппинг.

**Риск:** если `obs()` пишет «порядковый номер сезона по константе» (summer=0), а
каталог/маски строятся по `work_seasons` из данных (где порядок summer/autumn/winter/
spring, data.cpp:50-56), то индексация `catalog_by_season_[s]` и маски «работают в
одном соглашении», но само число в obs не совпадает с семантикой «весна=0». Это не ломает
обучение (модель выучит отображение), но ломает интерпретируемость и любой внешний код,
сверяющий season по `constants.h`. **Рекомендуется:** зафиксировать единый порядок и
документировать, либо явно маппить. **Серьёзность: minor/major (проверить заголовок).**

### [m-E6] `restore_all` — теоретическая неполнота (game.cpp)

**Место:** `game.cpp:493-564`. Частичный ремонт через `while(true)` корректно завершается,

### [m-E7] `busy_people` вычисляется до событий/переполнения (game.cpp)

**Место:** `game.cpp:330-334` vs `339-353, 388-390`. `busy_people = people - free`

расходиться с реальностью в тот же день. **Серьёзность: minor.**

## ЧТО СДЕЛАНО ХОРОШО

- **Детерминизм копирования состояния.** `Game(const Game&)` и `operator=` (game.cpp:101-157)
  глубоко копируют `rng`/`rng_np`, `base_index_map_`, `undo_` → корректный `reset()` и
  snapshot для RL.
- **Верная реализация генераторов.** `MtRandom` (rng.cpp:12-136) — точный порт CPython MT
  (включая отрицательные seed, rng.cpp:47-62); `PCG64`+`binomial` (rng.cpp:195-394) — порт
  numpy. Критично для воспроизводимости обучения.
- **Аккуратная работа с порядком вычисления аргументов в C++** в `earth.cpp:132-145` —
  автор вынес `randint` в именованные переменные из-за неопределённого порядка eval (MSVC
  справа-налево). Хорошая практика.
- **`find_lot`** (env.cpp:200-336) — обращения к соседям корректно ограничены
  (`x>0`, `x<ms-1`, `y>0`, `y<ms-1`), переполнения нет.
- **`base_in_box`** (game.cpp:186-200) — корректная проверка границ и диапазона индекса
  перед разыменованием.
- **SB3-порядок RMS** в `ColonyVecEnvCpp::step_wait_batch` (env.cpp:815-891) — update RMS по
  old obs, затем нормализация по old RMS, сохранение raw для `terminal_observation`.
  Корректно.
- **`delete_base`** (game.cpp:295-307) — корректный swap-and-pop, `base_index_map_`
  обновляется верно (проверено вручную; см. `05_false_positives_and_notes.md`).
