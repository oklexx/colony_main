## ЛОЖНОПОЛОЖИТЕЛЬНЫЕ НАХОДКИ (проверено вручную — багов НЕТ)

### [FP-1] `Game::delete_base` НЕ ломает `base_index_map_` (game.cpp:295-307)

Автоматический обзор пометил это как **critical** («при удалении любой не-последней базы
`base_index_map_` копится неверно → фантомные базы / невозможность взаимодействия»).
**Проверка показала, что код КОРРЕКТЕН:**

```cpp
295: void Game::delete_base(Base& b) {
296:     destroyed_lots[(size_t)b.y * map_size_ + b.x] = 12;
297:     size_t idx = (size_t)(&b - bases.data());
298:     size_t last = bases.size() - 1;
299:     if (idx != last) {
300:         Base& moving = bases[last];
301:         std::swap(bases[idx], bases[last]);
302:         base_index_map_[(size_t)moving.y * map_size_ + moving.x] = (int32_t)idx;
303:     }
304:     bases.pop_back();
305:     base_index_map_[(size_t)b.y * map_size_ + b.x] = -1;
306:     invalidate_caches();
307: }
```

Это стандартный **swap-and-pop**:
- `idx = &b - bases.data()` — индекс удаляемой базы `b`.
- `last = bases.size()-1`.
- Если `idx != last`: свопаем `bases[idx]` и `bases[last]`. Теперь `b` (удаляемая) стоит на
  позиции `last`, а `moving` (бывшая последняя) — на позиции `idx`.
- `base_index_map_[moving.y * ms + moving.x] = idx` — карта для `moving` указывает на её
  НОВУЮ позицию `idx`. **Верно.**
- `bases.pop_back()` удаляет элемент на позиции `last`, т.е. `b`. **Верно.**
- `base_index_map_[b.y * ms + b.x] = -1` — клетка удалённой базы помечена пустой. **Верно.**

Итог: фантомных баз нет, живая база `moving` корректно адресуется. **Это НЕ баг.**
Автоматическая находка была ложноположительной (вероятно, ошибка при чтении swap-логики).

> ⚠️ Единственное тонкое место: строка 305 читает `b.y`/`b.x` **после** потенциального свопа.
> После `std::swap(bases[idx], bases[last])` ссылка `b` указывает на `bases[last]` (теперь это
> удаляемый объект), и `b.y`/`b.x` — валидные поля этого объекта до `pop_back()`. Чтение
> происходит ДО `pop_back()`, поэтому UB нет. Но это хрупко: если когда-либо `b` будет
> использоваться ПОСЛЕ `pop_back()`, будет use-after-free. Рекомендуется сохранить координаты
> до свопа: `int bx = b.x, by = b.y;` и использовать `bx,by` в строке 305 для ясности.

### [FP-2] Размерность observation/action согласована (не баг)

Автоматический обзор пометил как «major (verify)» возможное рассинхронизация `obs_size()`/
`n_actions()` с реальным наполнением. **Проверка покомпонентная показала ПОЛНОЕ совпадение:**
- `obs_size() = 27 + n_build + 7 + 9 + 4*n_build = 43 + 5*32 = 203`, и `obs()` делает ровно
  столько `push` (env.cpp:420-450). Совпадает.
- `n_actions = A_BUILD0 + n_build + N_MANAGERS = 2 + 32 + 11 = 45`, и `cpp_env.py`
  (`_action_names`) содержит `["DAY","WEEK"] + 32 build + 11 manager` = 45. Порядок менеджеров
  в `env.step` (`manager_base_+0..10`) совпадает с именами в `cpp_env.py:86-88`. Совпадает.

Этот класс багов (частая причина «модель не учится») здесь **отсутствует**. Хорошо.

## ОБЩИЕ ЗАМЕЧАНИЯ (архитектура / процесс)

### [G-1] Имя `AsyncTrainer` вводит в заблуждение
Класс синхронный (M-RL2 в `03_rl_training.md`). Либо реализовать async (пул воркеров C++ /
процессов, очередь, push весов), либо переименовать в `Trainer`/`SyncTrainer` и убрать
`queue_size` из конфига.

### [G-2] Нет единого источника правды для гиперпараметров наград
`reward.json` ≠ дефолты в коде (M-D1). Риск рассинхрона при экспериментах. Рекомендуется:
всегда грузить `reward.json`, убрать дублирующие дефолты, удалить `curriculum_rewards`.

### [G-3] Отсутствует `.gitignore`
Папки `build/`, `*.pyd`, `*.exe`, `saves/`, `~/colony_runs` не игнорируются. Рекомендуется
добавить `.gitignore`.

### [G-4] Тестирование
`tests/test_gae.py` написан в той же неверной конвенции, что и код (C-G1). После исправления
GAE нужно переписать `reference_gae` под transition-based dones. Остальные тесты
(`test_ppo_smoke.py`, `test_integration.py`, `bench_per_step.py`) — полезны, но не ловят
основной баг маски.

### [G-5] Воспроизводимость
- C++ RNG сеется детерминированно (MtRandom/PCG64 точные порты) — хорошо.
- PyTorch НЕ сеется (`torch.manual_seed` не вызывается, m-RL6) — прогон модели не воспроизводим.
- `net_worth` кэш не сбрасывается в reset (OK-1) — награда недетерминирована между эпизодами.

### [G-6] Перенос нормализации
`RunningMeanStd` (VecNormalize) реализован в C++, но `save_normalization` не вызывается из
`train.py` (m-RL7). При деплое агента на новый запуск статистика нормализации будет «с нуля»,
что ломает инвариантность признаков. Нужно сохранять и загружать RMS вместе с весами.

## VERDICT

Проект имеет **крепкое ядро** (детерминированный RNG, согласованные размерности
observation/action, корректный swap-and-pop, стандартный PPO-clip), но содержит **несколько
критических багов**, из которых главные — **порча GAE-преимуществ (C-G1/C-G2)** и **искажение
награды из-за кэша net_worth (C-E1)** — напрямую ухудшают/ломают обучение RL, а **GUI/main
(C-C1/C-C2/C-C3)** ломают интерактивное использование. После правок из чеклиста проект
станет пригодным и для игры, и для тренировки агента.
